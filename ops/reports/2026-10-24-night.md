## Features
- **`mtdi update`**:
  - pulls the latest MTDI, fast-forward only;
  - reinstalls packages only when `pyproject.toml` changed, and only inside a venv;
  - restarts the autostart service, then runs a quick doctor. `--check` only looks.
  - stops with a plain reason, instead of overwriting or merging, when MTDI's own files have edits, when the copy has its own commits, or when the network stalls (git calls time out after 120 s);
  - never touches your projects.
- **Page-ready signal**:
  - `<html data-page-ready="1" data-page-ready-ms=…>` once a page has mounted, the boot screen is gone, no callback is loading and the page has stopped changing;
  - the tour judges each page on it instead of a fixed 8 s sleep;
  - the new phone pass (390×844, touch) hit-tests every nav button and makes a real tap. It passed its first four runs, and in #42 I called it stable. That was wrong: the fifth run failed. See Struggles.
- **Studio words (S1-06, first slice)**:
  - 42 words come from `studio/content/default.json`: the brand, author credit, nav, boot screen, intro, Home hero and cards, and every page's eyebrow, title and subtitle;
  - they can be overridden by `MTDI_CONTENT` or a project's `interface` block; `mtdi check` reports unknown keys and wrong types;
  - with no overrides, every page renders exactly as before;
  - verified in Chromium through `mtdi run`: "GREENHOUSE", "CLIMATE", "Air and soil".

## Bugs found and fixed
- **Launcher (shipped in #38):** `python -m mtdi` imports from the current folder first. Run from inside any folder that held an `mtdi/` directory, MTDI ran that code instead of the installed copy. The end-to-end update test caught it: the update ran against the wrong repository. The launcher, the systemd unit and the launchd agent now use `-P`.
- **Page-ready signal, first version:** on a phone it said "ready" while the boot screen still covered every nav button. The phone pass caught it, and the signal now waits for the boot screen.
- **Security (#43, first commit only, never on main):** the scrub hero put configurable words into the page with `innerHTML`. A project file could have injected markup (CWE-79). It now uses `textContent`. In Chromium, a hostile title rendered as literal text and its `onerror` never ran.

## Struggles
- **Software graphics in the cloud are slow.** The 3D pages block the browser for tens of seconds: page 1 is ready after about 33 s and the MTDI page after about 13–15 s. After the phone tap, the MTDI page took 66–106 s to be ready. That is why the page never declares its own timeout; the waiting tool sets the deadline (180 s).
- **Self-inflicted interruptions:** a stray `git stash` nearly pulled the new tour script out from under a running tour, and a `git checkout --` threw away a fix that I then had to re-apply. Both were caught before anything shipped. I now keep other branches in separate worktrees while a long run is going.

- **The phone pass was not stable after all.** On a phone, the studio's head script sets the viewport meta to the 1180 px desktop composition. The meta was identical and correct in every run, yet Chromium's device emulation applied it in only some fresh contexts (1 of 5 in one probe, 2 of 3 in another). Elsewhere the layout stayed 390 px wide and the nav check failed. Replacing the meta element instead of editing it made things worse (0 of 5). The tour now checks that precondition first. It retries an attempt where the viewport wasn't applied in a fresh context, and reports skipped (never passed) if none applies it.

## Weaknesses
- The installer and `mtdi update` have only run on cloud Linux. A real Pi and a real Mac are still untested.
- Most studio placeholders are still there: section bodies, the "Title / Text" cards, CHANNEL 1 / BUTTON tabs and LABEL tiles.
- The 128-channel snapshot is still above 100 ms in the cloud.
- Whether real phones apply the studio's script-set viewport is unverified; the emulator often does not. Sending the right viewport meta from the server for phones, instead of changing it by script, would remove the question.
- The page load times above are from software rendering. The Pi 5's GPU should do better, by an amount I don't know yet.
